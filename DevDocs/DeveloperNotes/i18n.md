# Internationalization

This document tells you how to name and how to organize the i18next
translation keys in `src/main/webapp/ui`. It also tells translators how to add
a language, and how to see that language in a running RSpace instance.

Keep the keys simple and consistent. Simple keys are easy to find, to use
again, and to check with the lint tools.

## The setup

The shared i18next object is in `src/modules/common/i18n/index.ts`. The English
text is in JSON catalogues in
`src/modules/common/i18n/locales/en-US/<namespace>.json`. **The code uses keys.
The code does not use English text.**

The configuration sets `defaultNS` to `common`, `keySeparator` to `.`, and
`nsSeparator` to `:`. The build makes the TypeScript types from the catalogues.
Thus the compiler checks each key that the code uses.

## 1. Use one namespace for each module

Each catalogue file is a namespace. The namespaces agree with the modules of
the application:

| Namespace   | Use for the text in ...                              |
| ----------- | ---------------------------------------------------- |
| `common`    | Shared user interface: buttons, dialogs, the application bar, errors, and other text that more than one module uses |
| `workspace` | The ELN workspace                                    |
| `inventory` | The Inventory module                                 |
| `gallery`   | The Gallery                                          |
| `apps`      | The Apps and integrations pages                      |
| `groups`    | The Groups pages                                     |
| `system`    | The System and sysadmin pages                        |
| `dashboard`, `admin`, `about`, `public` | The applicable pages   |

**Put a key in the namespace of the module that shows the text.** Move the key
to `common` only when a different module must show the same text. Do not put a
key in `common` before a second module needs it.

## 2. Name the keys correctly

Group the keys by feature or by component. Then name the function of the text:

```
<feature>.<subFeature>.<leaf>
```

- Write each part in `camelCase`, for example `emptyTablePlaceholder` or
  `insertTooltip`.
- The last part gives the function of the text. It does not give the English
  words. Use `validation.nameRequired`. Do not use `pleaseEnterAName`. The
  words can change, but the key must stay the same.
- Group the keys below the component or the feature that owns the text. This
  example comes from `common`:

  ```json
  "stoichiometry": {
    "addReagent": {
      "title": "Add New Chemical",
      "validation": { "nameRequired": "Name is required" }
    },
    "dialog": { "reactionTable": "Reaction table" }
  }
  ```

- Use the general keys that are available, for example `actions.save`,
  `actions.cancel`, and the `alerts.*` keys. Do not add a different key such as
  `saveButton` or `cancelBtn`. Examine the groups in `common` (`actions`,
  `alerts`, `inputs`, `confirmationDialog`, and the other groups) before you
  add a new key.

## 3. Refer to the keys in the code

In a React component, use the hook. A key without a namespace uses the default
namespace:

```tsx
const { t } = useTranslation();          // defaultNS = common
t("actions.save");                        // a key in common
t("inventory:sample.namePlaceholder");    // a key in a different namespace
```

To use a different namespace many times, give the namespace one time at the
top of the component:

```tsx
const { t } = useTranslation("inventory");
```

Outside React, for example in a service, a TinyMCE plugin, or a simple module,
use the shared object. **Always write the namespace:**

```ts
import i18n from "@/modules/common/i18n";
i18n.t("common:stoichiometry.plugin.insertTooltip");
```

Use the `common:` prefix. Do not use `getFixedT(null, "common")`. The prefix is
easier to read, and the compiler continues to check the key.

## 4. Do not assemble the keys

Write each key fully. Do not assemble a key from parts. Do not select a key
inside `t()` with a conditional operator. An assembled key is difficult to
extract, to type-check, and to find.

```ts
// do not do this: the call site assembles or selects the key
t(`errors.${code}`);
t(isPi ? "role.pi" : "role.user");

// do this: select between two complete t() calls
isPi ? t("role.pi") : t("role.user");
```

If the software must select a key while it operates, for example from an enum,
map the values to complete keys with `as const`. Each key stays visible, and
the compiler checks each key:

```ts
const keys = {
  missingLink: "common:stoichiometry.inventoryUpdate.linkRequired",
  insufficientStock: "common:stoichiometry.inventoryLink.insufficientStock",
} as const;
return i18n.t(keys[reason]);
```

## 5. Use interpolation. Do not join text.

Do not make a sentence from two or more translated parts. The word sequence is
different in each language. Use a placeholder or an ICU expression:

```json
{ "itemsSelected": "{count, plural, one {# item} other {# items}} selected" }
```

If the text contains markup, for example a link or `<strong>`, use
`TransRichText`. Do not divide the text.

The format of a list also changes with the language. Do not make a
user-visible list with `array.join(", ")`, and do not write the final `and` or
`or` yourself. Use `formatList` from `@/modules/common/i18n/listFormat`, and
give it the active i18next language:

```ts
formatList(names, i18n.resolvedLanguage ?? i18n.language);
```

You can continue to join items with a delimiter for machine formats. Examples
of machine formats are CSV, query parameters, database fields, CSS, and paths.

### Make the placeholder names agree

This project uses ICU interpolation. Thus a placeholder has **one** brace on
each side (`{types}`). It does not have two braces (`{{types}}`).

The placeholder name in the JSON must agree with the object key that you give
to `t()`. If the two names do not agree, you get no error. The user sees the
placeholder text:

```json
"canStoreOnly": "This container can only store {types}."
```

```ts
// wrong: the key does not agree with the placeholder name. The user sees
// "This container can only store {types}."
t("moveToTarget.messages.canStoreOnly", { canStoreLabel });

// correct
t("moveToTarget.messages.canStoreOnly", { types: canStoreLabel });
```

An unused value has the same effect. You can remove a placeholder from the
English text, but keep the value in the call. The software then ignores that
value. You get no error and no lint message.

`i18n:lint` examines the structure of the keys. It does not compare the
placeholder names with the arguments that you give to `t()`. **After you add or
change a message that has a placeholder, examine the feature in a browser.**

## 6. The procedure to add or to change a key

The two procedures that follow give the same result: a semantic key in the
code, and the English text in the `en-US` catalogue. Select the procedure that
agrees with your task:

| Your task | Procedure | Example |
| --------- | --------- | ------- |
| You use a message that is available | Key first | A new button can use `t("actions.save")`. You write no English text. |
| You change the words of a message | Key first | Keep `dialog.delete.title` in the code, and change the value in the catalogue. |
| You add text that is already agreed | Key first | Add `samples.emptyState.title`, extract the empty key, then write the value. |
| You write the text while you build a component | English first | Keep `"No samples match these filters"` adjacent to its temporary key while you work. |
| You add several messages that occur one time | English first | Write a dialog title, an explanation, and a confirmation label. Then extract all of them together. |
| You write a new ICU message | English first | Write the full plural or interpolation expression adjacent to its values. |

If the two procedures are equally easy, use the key-first procedure. It needs
no temporary value, and it cannot replace an English value that is already in
the catalogue.

### Key first: add the key, then add the English text

Start with a semantic key in the component:

```tsx
const { t } = useTranslation("inventory");

return <Button>{t("samples.createDialog.submit")}</Button>;
```

Run `i18n:extract`. The extractor puts an empty entry in
`src/modules/common/i18n/locales/en-US/inventory.json`:

```json
{
  "samples": {
    "createDialog": {
      "submit": ""
    }
  }
}
```

Write the English value in the catalogue. Do not change the component:

```json
{
  "samples": {
    "createDialog": {
      "submit": "Create sample"
    }
  }
}
```

Run these commands from the root of the repository. The `i18n:*` scripts change
to `src/main/webapp/ui` for you:

```bash
pnpm run i18n:extract # writes the new keys, with empty values, into the catalogues
# write the English text in locales/en-US/<namespace>.json
pnpm run i18n:types   # makes i18next.d.ts and resources.d.ts again
pnpm run i18n:lint    # shows the keys that are absent or incorrect
pnpm run i18n:check   # makes sure that extraction finds no more changes
pnpm run tsc          # makes sure that the key references compile
```

`i18n:extract` does not replace an English value that is available, and it does
not delete an unused key. Thus you can run it frequently. `i18n:check` is the
command for the CI build. Extraction and lint ignore the keys in `__tests__`,
`*.test.*`, `*.spec.*`, and `*.story.*`.

### English first: write the text, then extract it

If it is easier to write the text in the component, add the text temporarily as
a `defaultValue`. Select the final semantic key now. The extractor cannot make
a good key from an English sentence.

```tsx
const { t } = useTranslation("inventory");

return t("samples.createDialog.title", {
  defaultValue: "Create a sample",
});
```

For a message that has a placeholder, put the ICU text in `defaultValue`, and
give the value of the placeholder in the same call:

```tsx
t("samples.resultsCount", {
  defaultValue: "{count, plural, one {# result} other {# results}}",
  count,
});
```

From the root of the repository, extract these values into the `en-US`
catalogues:

```bash
pnpm run i18n:extract --sync-primary
```

`--sync-primary` can change an English value that is available, and it can also
add a new value. Examine the changes to the catalogue, and make sure that only
the intended messages changed. Do not use `--sync-all`, because `--sync-all`
also deletes the applicable values in the other languages.

When the English text is in the catalogue, remove `defaultValue` from the
source. The completed code then contains only keys:

```tsx
return t("samples.createDialog.title");
```

Then make the types again, and do the checks:

```bash
pnpm run i18n:types
pnpm run i18n:lint
pnpm run tsc
```

For a group of strings, the same extraction can operate continuously, and make
the types again after each change to a catalogue:

```bash
pnpm run i18n:extract --sync-primary --watch --with-types
```

Stop the extractor. Then remove the temporary values, and run `i18n:lint` and
`tsc` before you finish. `i18n:extract` cannot read the text in JSX. Put each
English string in a `t()` call, as shown above.

## 7. The procedure for translators

The translation catalogues are in
`src/modules/common/i18n/locales/<language>/<namespace>.json`. `en-US` is the
source language. Each other language must have the same file names, the same
object structure, and the same keys as `en-US`. Translate only the values.

### Add a new language

Use a BCP 47 language tag, for example `fr-FR` or `de-DE`.

1. Add the language tag to `locales` in
   `src/main/webapp/ui/i18next.config.ts`.
2. Make the directory `src/modules/common/i18n/locales/<language>/`.
3. Copy each JSON namespace from `locales/en-US/` into the new directory, and
   translate the values.
4. Run these commands:

   ```bash
   pnpm run i18n:lint
   pnpm run i18n:status
   pnpm run tsc
   ```

Keep `fallbackLng` set to `en-US`, unless the product owner approves a
different fallback language.

### Translate the strings of a new feature

Do these steps for a feature that developers added after your language existed:

1. Run `pnpm run i18n:check`, to put the new keys in the catalogues.
2. Run `pnpm run i18n:status`, to see the values that are absent or
   untranslated.
3. Translate the new values in each language that is not `en-US`.
4. Run `pnpm run i18n:lint` before you deliver the translation.

Do not change a key to agree with the translated words. If the English words
change, but the meaning stays the same, keep the key and change the values.

### See your translation in a running instance

RSpace has one locale for the full instance. A user cannot select a different
locale yet. To see your translation, set the experimental locale property, then
start the application again.

The property is in the `deployment.properties` file of the instance. The
application reads this file from the directory that the
`propertyFileDirPlaceholder` property gives. See
`applicationContext-resources.xml`. The default values are in
`src/main/resources/deployments/defaultDeployment.properties`.

1. Open `deployment.properties`.
2. Set the property to your BCP 47 language tag:

   ```properties
   deployment.experimental.locale=fr-FR
   ```

3. Start RSpace again. The application reads the property one time, when it
   starts.
4. Examine the pages that show your translation.
5. When you complete the examination, make the value empty again:

   ```properties
   deployment.experimental.locale=
   ```

These rules apply to the property:

- An empty value gives `en-US`. This is the default.
- The value must be a BCP 47 language tag, for example `fr-FR`, `de-DE`, or
  `en-US`.
- If the value is not a valid tag, RSpace writes a warning in the log and uses
  `en-US`. RSpace does not stop.
- If a catalogue for the language does not exist, RSpace shows the `en-US`
  text. Thus a partial translation shows two languages together. This is
  correct behavior, and it shows you the values that you must still translate.
- The property changes the language of the server messages, of the email
  templates, and of the legacy JavaScript messages. It also selects the
  `legacyMessages.<locale>.js` file that the browser receives.
- The property is experimental. Use it to examine a translation. Do not use it
  on a production instance until a user can select a locale.

`UserLocaleService` reads this property. To find this behavior in the code,
start at that class.

### What translators must keep

- Keep the JSON keys, the object structure, the punctuation that JSON needs,
  and the namespace file names.
- Keep each placeholder exactly, for example `{name}`, `{count}`, and
  `{serverAlias}`.
- Keep the ICU syntax and the ICU option names exactly. Two examples are
  `{count, plural, one {...} other {...}}` and
  `{enabled, select, yes {...} other {...}}`.
- Keep the names of the rich-text tags and their necessary attributes.
  Translate only the text between the tags. Change a URL only when the target
  for your language is different.
- Do not add other HTML. `TransRichText` gives the permitted tags. These
  include `<strong>`, `<br/>`, `<code>`, `<kbd>`, the list tags,
  `<internalLink to="...">`, `<externalLink href="...">`, and
  `<helpDocs docLink="...">`.
- Keep the product names, the integration names, the API names, and the legal
  terms in English. Translate such a name only if an approved translation is
  available.

### Links and documentation targets

`common.help` is the central map of the HelpDocs articles. Each value is a
HelpDocs path, and it can also have an anchor, for example
`"c8sxesdqpy-create-a-template#update_all_of_your_samples_to_latest_template_version"`.

Each value in `common.help` is one documentation target:

- If your language uses the same HelpDocs article and the same anchor, copy the
  `en-US` value. Do not change it.
- If your language has its own HelpDocs pages, replace the full value with the
  applicable `slug#anchor`.
- Keep the slug and the anchor together in `common.help`. Do not put a HelpDocs
  slug in the text of a feature.
- In text, refer to the documentation with
  `<helpDocs docLink="commonHelpKey">...`. Do not use a URL or an `<a>` tag.

Use `<internalLink to="/path">...` for a link in the application. Use
`<externalLink href="https://...">...` for a link to a different web site. The
renderer supplies the route and the necessary attributes for an external link.
Thus do not add `target`, `rel`, or an `<a>` tag to a value in a catalogue.

## 8. The `noJsxLiterals` rule finds the text that you did not translate

The Biome rule `style/noJsxLiterals` has the severity **error**. See
`src/main/webapp/ui/biome.jsonc`. A literal string in JSX shows that the code
gives English text directly to the user, and not through a key. If
`noJsxLiterals` fails, the text needs a key.

```tsx
// fails noJsxLiterals: the English text is in the code
<Button>Save</Button>

// correct: the text comes from a key
<Button>{t("actions.save")}</Button>
```

Do not disable this rule to permit literal text. A rare exception is a symbol,
or a character that is not a word. For such a character, use the
`allowedStrings` option of the rule in an `overrides` entry.
`IdentifierPublicPage.tsx` does this for `"˚"`. If the text contains words, add
a translation key.

## 9. Frequent errors

- **A test replaces i18next with a mock.** The test then examines the mock, and
  not the ICU format, the fallback language, the interpolation, or the contents
  of the catalogue. Use the configured object in `cimode`. As an alternative,
  use `renderWithRealI18n` or `createTestI18n` from `src/__tests__/helpers`
  when the translated text is important. A test for the legacy `RS.msg`
  function must use the real formatter and a real entry in the catalogue.
- **The code joins a user-visible list with `join`.** Use `formatList`. The
  punctuation and the conjunctions are different in each language.
- **The placeholder name does not agree** with the object that the code gives
  to `t()`. The user sees the text `{placeholder}`, and the software gives no
  error. See section 5.
- **A value is no longer necessary** after you make the English text more
  simple. If the ICU string no longer uses `count`, `placed`, or `total`, the
  message does not show that value.
- **The developer does not run `i18n:types` after a change to a JSON file.**
  `tsc` can then agree with an old key name, or it can fail for a key that
  exists.
- **The developer writes a new key in the JSON file first.** Write the `t()`
  call first. Then use the key-first procedure or the English-first procedure
  in section 6. This prevents spelling errors, an incorrect structure, and keys
  that do not agree with the code.

## The steps for a new string

1. Find the module that shows the text. Use the namespace of that module. Use
   `common` only if more than one module shows the text.
2. Look for an equivalent key. If a key exists, use it again.
3. Name the key `feature.subFeature.roleOfText` in `camelCase`.
4. Refer to the key with `t()` in a component, or with `i18n.t("ns:key")`
   outside React.
5. Use a placeholder for each value. Do not join text.
6. Use `formatList` for a user-visible list. Do not use `join`.
7. Use the real i18next object in the tests. Do not use a mock.
8. Use the key-first procedure. As an alternative, write a temporary
   `defaultValue`, and extract it with `i18n:extract --sync-primary`. Then run
   the types command, the lint command, and `tsc`.
