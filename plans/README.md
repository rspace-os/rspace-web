## Findings considered and rejected

- **Store Booking settings in `UI_JSON_SETTINGS`**: rejected. Its generic Ajax
  endpoint and client-side read/modify/write cycle do not provide a typed,
  atomic REST v2 contract. Plan 008 reuses `UserPreference` storage behind a
  dedicated Booking manager and current-user endpoint instead.
- **Create a second user-preference table or generic REST collection**:
  rejected. The existing `UserPreference` value is already large enough for
  one versioned Booking document; a Booking-specific service is the narrower
  ownership seam.
- **Delete or rewrite each item timezone when adding display preferences**:
  rejected. The item value still defines opening-hour validation, closure
  calculation, and calendar feed metadata. Plan 008 makes it read-only at the
  public UI/API seam while retaining it internally.
- **Apply the Booking timezone preference to every legacy RSpace page**:
  rejected for this iteration. The JSP/session timezone mechanism has a much
  wider rendering and export surface and requires its own migration plan. Plan
  008 uses the JVM timezone for the Institution option, matching the legacy
  missing-session fallback without changing valid browser/session zones.
- **Keep Booking synchronized with Inventory/workspace permissions**: rejected.
  It would give one resource two authorities, make a valid Booking grant change
  when unrelated Inventory sharing changes, and prevent a Booking-only Viewer.
  Plan 013 keeps creation eligibility and an explicit opt-in ownership-transfer
  command, but no continuous sync or read-time intersection.
- **Build Booking permissions on the legacy record ACL**: rejected. Its record
  propagation and workspace/group semantics do not express one direct role per
  grantee, dynamic All users, a separate access version, or Booking-specific
  capabilities without compatibility branches.
- **Create Booking-only permission tables**: rejected because the next adopter
  would require another schema and editor migration. Plan 013 makes persistence,
  replacement, resolution, audit, REST, and UI generic now and proves both
  layers with a second test-only scheme.
- **Use one global `(resourceType, resourceId)` grant table**: rejected because
  the database could not enforce that the protected resource exists or owns its
  access aggregate. Each protected entity instead holds a real foreign key.
- **Expose full Instruments to Booking-only users**: rejected. Plan 013 adds a
  relationship-only safe Booking target summary and does not grant Inventory
  route access.
- **Add bulk access changes to All Items or the admin page**: rejected for this
  iteration. Access replacement is item-scoped and atomic; existing sysadmin
  bulk configuration actions remain limited to settings/enabled/archive.
- **Migrate other permission models in the same change**: rejected. Inventory,
  workspace, Gallery, forms, and records retain their current semantics until
  separate migration plans can preserve their invariants.
- **Persist departed-requester access**: rejected. A booking row already owns
  its requester relation. Plan 013 authorizes current role membership OR the
  represented requester for booking reads, so a marker table would duplicate
  state and incorrectly distinguish voluntary from involuntary role loss.
- **Persist assignment availability and fan identity changes out to every
  resource**: rejected. Live User/Group FKs determine effective access;
  `ON DELETE SET NULL` plus snapshots preserves hard-deleted identities. The
  existing user/group audit records lifecycle changes.
- **Use one global grantee-search route**: rejected. Search is scoped to the
  protected resource and requires assignment-management capability. Booking
  defaults use a separate sysadmin-only route backed by the same DAO query.
- **Add an Inventory-transfer preflight endpoint**: rejected. One filtered
  Booking configuration collection request can batch the selected Instrument
  ids and returned capabilities. The transfer command remains authoritative.
- **Create a generic caller-scoped-field framework**: rejected for one adopter.
  One optional REST `ResourceAccessSpec` contributes the query constraint,
  batched fixed fields, and access routes while the generic service module keeps
  a REST-free protected-resource interface.
- **Trust the controller's permission check during access mutation**: rejected.
  Membership, enabled state, or system role can change between a concealed REST
  lookup and the write. Plan 013 locks and re-resolves those authorization facts
  inside the mutation transaction and proves the race with integration barriers.
- **Round-trip read-side principal snapshots in PUT**: rejected. The write
  contract carries only grantee key and role; the server resolves live
  principals and owns names, status, inherited sources, and retained snapshots.
- **Permit All users to become Booking Owner or Manager**: rejected. A dynamic
  audience cannot provide accountable administration. Booking permits the
  audience only for Booker and Viewer, while the generic scheme contract keeps
  allowed grantee kinds configurable per role.
- **Claim atomic or durable audit delivery through the current audit service**:
  rejected. The existing service is log-backed and notified after commit. Plan
  013 tests its real success/rollback/no-op behavior and leaves a transactional
  audit outbox as a separate cross-cutting design.
