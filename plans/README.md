## Findings considered and rejected

- **Store Booking settings in `UI_JSON_SETTINGS`**: rejected. Its generic Ajax
  endpoint and client-side read/modify/write cycle do not provide a typed,
  atomic REST v2 contract. Plan 008 reuses `UserPreference` storage behind a
  dedicated Booking manager and current-user endpoint instead.
- **Create a second user-preference table or generic REST collection**:
  rejected. The existing `UserPreference` value is already large enough for
  one versioned Booking document; a Booking-specific service is the narrower
  ownership seam.
- **Delete or rewrite each item timezone when adding display preferences**:
  rejected. The item value still defines opening-hour validation, closure
  calculation, and calendar feed metadata. Plan 008 makes it read-only at the
  public UI/API seam while retaining it internally.
- **Apply the Booking timezone preference to every legacy RSpace page**:
  rejected for this iteration. The JSP/session timezone mechanism has a much
  wider rendering and export surface and requires its own migration plan. Plan
  008 uses the JVM timezone for the Institution option, matching the legacy
  missing-session fallback without changing valid browser/session zones.
- **Incremental or dual-stack production rollout**: rejected. The backend is
  migrated codebase-wide in one branch and one production cutover so Shiro and
  Spring cannot disagree about identity, sessions, URLs, or permissions. The
  large blast radius is controlled with characterization tests and workstream
  gates inside the branch, not by shipping intermediate architectures.
- **Represent every permission as a `GrantedAuthority`**: rejected because the
  RSpace permission grammar includes object ids, properties, groups,
  communities, locations, `${self}`, disabled grants, ACL fallback, public-link
  rules, and WRITE-implies-READ semantics.
- **Keep both Shiro and Spring request filters authoritative in production**:
  rejected because disagreement between two URL/session decision systems would
  create ambiguous failures and possible authorization gaps.
- **Enable CSRF during the backend-only phase**: deferred because the unchanged
  JSP/React forms do not currently send Spring CSRF tokens. Preserve current
  behavior explicitly and enable CSRF in the UI phase.
- **Upgrade password hashes during the framework migration**: deferred. Match
  the existing salted SHA-256 format first; migrate hashes separately after
  authentication parity is proven.
- **Change AJP, proxy, IdP, remote-header, or SSO attribute configuration**:
  rejected as outside phase-one scope. The existing `RemoteUserRetrievalPolicy`
  interface is the unchanged application seam.
- **Add remember-me support**: rejected. RSpace does not request Shiro
  remember-me behavior and the login UI has no remember-me control.
- **Rotate the committed monitoring credential as part of this migration**:
  important but independent. Rotate and externalize the credential at
  `src/main/webapp/WEB-INF/web.xml:135` in a separate operationally coordinated
  security change; never copy it into Spring configuration.
